## Phase Boundary

설계 10-1 "만드는 순서" 4번: **틀 자동화(기록·실행·제출 확인·알림 창·막힘)와 활동 기록**을 Phase 1~3의 MV3 확장 위에 더한다. 이용자가 반복 업무를 한 번 해 보여 틀로 저장하고, 이후 "틀 고르기 1번 + 바뀌는 값 2~3번 + 제출 확인 1번"으로 끝내며, 되돌릴 수 없는 제출은 항상 확인 뒤에만 한 번만 일어나고, 문제가 생기면 활동 기록으로 추적할 수 있어야 한다.

요구사항: TMPL-01~16, LOG-01~03 (ROADMAP Phase 4).

**이 단계의 틀은 이용자가 보고 있는 탭(앞 탭)에서만 돈다.** 뒤쪽 탭에서 돌리기(BG-01~02), 틀마다 이미지·광고 차단(BG-03), 작업판(BORD), 반복 패턴 알림(PATN-01)은 Phase 5다. Phase 4는 Phase 5가 그대로 쓸 수 있게 실행 상태를 "탭 하나에 매이지 않는 실행 기록"으로 둔다(D-17).

설계 검토(CEO·디자인·엔지니어링)는 모두 끝났고, 설계의 모든 결정은 잠긴 결정이다(GSTACK REVIEW REPORT, "NO UNRESOLVED DECISIONS"). 다시 열지 않는다.

### 앞선 단계 의존 (이 계획은 미리 썼다)
이 계획은 Phase 1 실행 중(16개 중 12개 완료, 커밋 `f468b6e` 기준)이고 Phase 3 계획이 아직 조사 단계일 때(PR #9, 브랜치 `claude/phase3-plans-ng6f32`: CONTEXT·RESEARCH·PATTERNS만 있음) 미리 썼다. 실행 전에 아래가 끝났는지와 결과가 이 계획의 가정과 맞는지 확인하고, 다르면 이 계획을 먼저 맞춘다.
- **Phase 1 계획 13~16(아직 실행 전):** 사이트별 끄기·"도울 수 없음"·사이트별 동기화 항목, 형식 버전 변환 실패 보호·8KB, 옛 도우미 정리, 확대와 상관없는 오버레이 크기, 서체·50ms·독립 DOM 감사.
- **Phase 2 중간 이용자 시험:** 기본값과 이후 순서가 바뀔 수 있다. 틀 쪽 기본값(속도별 쉼 길이 등)은 Phase 2 결과를 보고 맞춘다.
- **Phase 3(가정 — 03-CONTEXT.md와 03-RESEARCH.md 기준):**
  - 명령판 `src/core/palette.ts`·`src/page/overlay/palette.ts`의 고정 카드 자리: 첫 장 3 "틀 실행", 둘째 장 4 "틀 기록", 셋째 장 3 "기록 내보내기"(Phase 3은 자리만 지키고 `implemented: false`). Phase 4가 이 세 카드에 동작을 붙인다.
  - 민감칸 판별 한 곳의 함수 `src/core/sensitive.ts`(`isSensitive`, Phase 3 D-26) — 틀 저장·활동 기록이 이것을 그대로 import한다.
  - 값 채우기 `src/page/input/fill-value.ts`(`fillValue`: 값을 넣고 입력 이벤트를 함께 발생) — 틀 실행의 입력 단계가 이것을 쓴다.
  - 최근 입력 값 저장(사이트 + 칸 이름, `chrome.storage.local`), 되돌리기(`src/core/undo-stack.ts`, 링크 이동 직후 Esc 뒤로·입력 되돌리기) — 활동 기록의 "되돌리기 횟수"가 여기서 나온다.
  - 옵션 페이지 `src/entrypoints/options/`와 파일 내보내기·가져오기 방식(`downloads` 권한 없이 확장 페이지의 `Blob` + `<a download>`, 가져오기는 파일 고르기) — 틀 파일·기록 파일도 같은 방식을 쓴다.
  - 설정 형식 `schemaVersion 2`(키 배치에 ←→ 포함, 컨디션 모드) — Phase 4가 필요한 설정(기본 속도 등)은 다음 형식 버전으로 더한다.
  Phase 3의 실제 파일 이름·함수 이름이 다르면 실행 전에 이 계획의 경로를 고친다.

## Implementation Decisions

### 구조 (Phase 1·3 결정 이어받기)
- **D-01:** Phase 1의 구조를 그대로 쓴다: 모든 프레임에 content script, 자주 일어나는 일은 그 프레임에서 바로, **명령판·확인 화면·틀 카드·진행 표시는 맨 위 프레임이 모아서** 띄운다. 프레임끼리의 메시지는 service worker를 거친다(설계 4장, 엔지니어링 검토 1번).
- **D-02:** 도우미는 `isTrusted` 입력에만 반응하고, 입력 필터(떨림 걸러내기)가 가장 먼저 받는다. 틀 카드·확인 화면·속도 바꾸기(←→)·멈춤(Esc)의 키도 같은 필터를 거친다(설계 5장·8장, 엔지니어링 검토 4번).
- **D-03:** 모든 저장은 service worker 하나가 순서대로 한다(단일 저장자). 새로 저장하는 데이터(틀, 실행 상태, 누름 기록, 활동 기록)에도 형식 버전을 붙이고, 형식 변환이 실패하면 원래 데이터를 그대로 두고 알린다(설계 7장, 엔지니어링 검토 6번).
- **D-04:** 저장 위치(설계 7장): 틀 = `chrome.storage.local`(동기화 용량을 넘을 수 있어서) + 파일 내보내기·가져오기. 틀 실행 상태 = `chrome.storage.session`. 제출 "누름" 기록 = `chrome.storage.local`(업데이트·재시작에도 지워지지 않게). 활동 기록 = `chrome.storage.local`, 하루 단위로 나눠 저장. 틀 기본 속도(전체 설정) = `chrome.storage.sync`. 서버로 보내는 것은 없다.
- **D-05:** 새 권한 없이 만드는 것을 목표로 한다(지금 권한: `storage`, `scripting`, `tabs`, `<all_urls>`). 꼭 필요하면(`webNavigation` 등) 새 권한이므로 이유 한 줄과 함께 만들 때 승인받는다. 새 의존성도 이유 한 줄 + 승인 후(저장소 규칙). 승인된 라이브러리: WXT, TypeScript, Preact, zod, Vitest, Playwright, IBM Plex Sans KR.

### 기록 (TMPL-01~03)
- **D-06:** 명령판 둘째 장 4 "틀 기록"으로 기록을 켠다. 기록 중에는 모드 표시에 "틀 기록 중"이 보이고, 같은 카드 자리(둘째 장 4)가 "기록 끝내기"로 바뀐다 — 자리는 옮기지 않는다(Phase 3 D-06 고정 자리). 끝내면 "틀 저장" 화면이 뜬다(설계 6.8).
- **D-07:** 기록기는 모든 프레임에서 이용자가 한 동작을 단계 목록으로 모은다: 누른 요소(직접 클릭, 자석 커서·번호표·머무르기로 도우미가 대신 누른 것 포함), 입력칸에 넣은 값(입력칸·선택 목록·체크·라디오·`contenteditable`), 페이지 이동. 단계는 service worker가 `storage.session`에 이어 적어서, 기록이 페이지 이동과 프레임을 넘어 이어진다.
- **D-08:** 시작 페이지 주소(기록을 켤 때 맨 위 프레임 주소)를 함께 저장한다(TMPL-04). 메뉴를 눌러 iframe 안 양식을 여는 회사 시스템도 있으므로, 기록 중 누른 메뉴도 단계로 남긴다.
- **D-09:** 요소 기억은 Phase 1의 식별 묶음(`src/core/fingerprint.ts`: id, name, 라벨 글자, 버튼 글자, aria, 페이지 안 위치 경로)에 **프레임 경로**(Phase 1 `selfPath`)와 프레임 주소를 더해 저장한다(설계 6.8 "요소 찾기").
- **D-10:** 민감한 칸(`src/core/sensitive.ts`의 판별, 이용자가 사이트별로 정한 것 포함)의 값은 틀에 저장하지 않고, 그 단계는 "직접 입력" 단계로 표시한다(설계 8장, PRIV-01, TMPL-14). 이용자가 푼 칸(비밀번호 칸 포함)만 값을 저장한다(Phase 3 D-27).
- **D-11:** "틀 저장" 화면(TMPL-02): 기록된 입력 단계를 번호 카드로 늘어놓고, 날짜·금액·전화번호처럼 모양이 뚜렷한 값은 "바뀌는 값" 후보로 미리 표시한다. 이용자는 칸 번호를 눌러 "매번 바뀜 / 항상 같음"을 바꾼다. 틀 이름은 타자를 줄이도록 후보(예: 제출 버튼 글자 + 페이지 제목)를 번호 카드로 고르고, "직접 입력"도 있다.
- **D-12:** 제출 성격의 버튼(기본 단어: 저장·상신·등록·제출·신청·전송 등, 사이트별로 고칠 수 있음) 중 **마지막으로 누른 것**을 "제출 단계"로 표시하고 이용자가 번호로 바꿀 수 있다(TMPL-03). 설계 8장 "제출 성격의 단계는 항상 이용자 확인 뒤에만"을 지키기 위해, 그 앞의 다른 제출 성격 단계(예: 임시저장)도 실행 때 확인을 거친다. 위험한 버튼(Phase 1 `danger.ts`) 단계도 실행 때 "정말 누를까요?" 확인을 거친다(설계 8장).

### 실행 (TMPL-04~08)
- **D-13:** 0 → 첫 장 3 "틀 실행" → 틀 목록 번호 카드(1~9, 9개 넘으면 다음 장) → 틀 번호. 틀이 없으면 "틀 기록" 카드(SYSTEM.md 상태 표).
- **D-14:** 바뀌는 값마다 후보를 번호 카드로 보여 준다: 그 값의 최근 값들(이 PC만, 민감칸 제외), 오늘 날짜(기록된 날짜 모양 그대로), 기록할 때의 값, 그리고 "직접 입력". 값을 다 받으면 저장된 시작 페이지로 메뉴를 거치지 않고 곧장 이동한 뒤(TMPL-04) 단계를 실행한다(TMPL-06).
- **D-15:** 요소 찾기(TMPL-05): 단계마다 프레임 경로로 프레임을 고르고, 식별 묶음 점수(`matchScore`)로 후보를 매긴다. **가장 높은 점수가 기준을 넘고 두 번째와 충분히 차이 날 때만** 확실하다고 본다. 확실한 요소가 없으면 누르지 않고 멈춘다(막힘, D-24). 기준값은 단위 시험으로 고정한다.
- **D-16:** 대신 누르기는 Phase 1 방식(`src/page/click/press.ts` `synthesizePress`: 마우스 누름·뗌·클릭과 포커스를 차례로)을 그대로 쓰고, 입력은 Phase 3 `fillValue`(입력 이벤트 함께)를 쓴다. 개발자 도구(`debugger`) 방식은 쓰지 않는다. 화면을 거치지 않고 사이트에 요청을 직접 보내지 않는다(설계 3장 "하지 않는 것").
- **D-17:** 실행 조정은 **service worker가 맡는다**(페이지를 넘나드는 단계, 잠들었다 깨어나기 때문). 페이지 쪽은 "이 프레임에서 이 단계 하기"만 하고 결과를 알린다. 실행 상태(어느 틀, 몇 번째 단계, 받은 값, 속도, 탭)는 **단계마다** `storage.session`에 적는다. 실행 기록은 탭 번호를 속성으로 가질 뿐 탭 하나에 매이지 않게 두어 Phase 5(뒤에서 실행)가 그대로 쓴다(설계 4장).
- **D-18:** 같은 틀은 한 번에 하나만 돈다(실행 잠금, TMPL-07). 이미 도는 틀을 다시 고르면 두 번째는 시작하지 않고, 그 틀이 도는 탭으로 옮겨 "이 틀은 이미 도는 중이에요"를 보여 준다. (작업판의 진행 상황으로 안내하는 것은 작업판이 생기는 Phase 5.)
- **D-19:** 속도 3단계(TMPL-08): 천천히(단계마다 멈추고 누르는 곳을 강조) / 보통(단계 사이 짧은 쉼) / 최대(쉼 없음). 기본값은 전체 설정(sync), 틀마다 따로 정할 수 있다. 실행 중 ←→로 바꾸고 Esc로 멈춘다. 모드 표시 자리에 단계 진행 막대 + "3/8 단계"와 지금 속도를 보여 준다(SYSTEM.md 상태 표 "틀 실행").
- **D-20:** **최대 속도:** 페이지 전체 로딩을 기다리지 않고 다음 단계의 요소가 나타나는 즉시 실행한다. 같은 화면(같은 프레임)에 있는 입력칸들은 한 번에 채운다(설계 6.8).
- **D-21:** 틀이 도는 동안에는 입력칸 안에 포커스가 있어도 **←→와 Esc를 도우미가 먼저 받는다**(실행기가 입력칸에 포커스를 옮겨도 속도 바꾸기·멈춤이 막히지 않게). 이용자가 직접 입력하는 단계(민감칸, 보안 키패드 등)에서 기다리는 동안에는 원래대로 글자가 들어간다.

### 제출 (TMPL-09~10, TMPL-13)
- **D-22:** 제출 단계 직전에 **항상** 멈춘다. Phase 1 확인 화면(`confirm-dialog.ts`, `confirm-guard.ts`)을 그대로 써서 입력한 값을 큰 글씨로 요약해 보여 주고(칸 이름 + 값, 민감칸은 "직접 입력함"), 1초 동안 모든 입력을 무시한 뒤 Enter(또는 스페이스바 1초 누르기)로 제출, Esc로 취소한다. 버튼 이름은 사이트 버튼 글자를 그대로 쓴다("Enter 상신")(설계 5장·6.8, SYSTEM.md 확인 화면·카피 규칙).
- **D-23:** **누르기 직전 기록:** 제출 버튼을 누르기 직전에 "누름" 기록을 `storage.local`에 쓰고, 저장이 끝났다는 답을 받은 뒤에만 누른다(엔지니어링 검토 2번). 누른 뒤 정해진 시간 안에 **페이지 이동 또는 성공 메시지가 화면에 나타나면** 성공("상신했어요" 토스트 + 활동 기록), 아니면 **다시 누르지 않고** "확인 필요" 카드(`--warning`, 다시 제출 버튼 없음)를 띄우고 틀을 멈춘다(TMPL-10). 성공 판정에는 페이지 쪽(main world) 알림 창 소식을 쓰지 않는다(D-27).
- **D-24:** service worker가 잠들었다 깨어나면 저장된 실행 상태에서 이어 간다. "누름" 기록만 있고 결과가 없으면 **다시 누르지 않고** "확인 필요"로 둔다(TMPL-13, 설계 4장·9장). 제출은 절대 다시 시도하지 않는다(설계 8장).
- **D-25:** 틀이 도는 동안에는 확장 업데이트 적용을 미루고(`runtime.onUpdateAvailable`), 틀이 모두 끝나면 적용한다(엔지니어링 검토 3번. Phase 1은 옛 도우미 정리와 `onInstalled` 다시 넣기만 했고 이 부분을 Phase 4로 넘겼다).

### 브라우저 알림 창 (TMPL-11)
- **D-26:** 알림 창 감시 장치는 페이지 쪽(main world)에 **모든 페이지·모든 프레임에 페이지가 열릴 때(`document_start`) 미리 넣어 두고**, 틀이 돌 때만 동작한다. 틀 밖 평소 사용에서는 가로채지 않는다(원래 창이 그대로 뜬다)(설계 6.8, 엔지니어링 검토 4번).
- **D-27:** 틀 실행 중 규칙: 확인한 제출 버튼을 누른 뒤 몇 초 안에 **처음 뜬 확인 창(confirm) 하나에만** "확인"으로 답한다. 그 뒤의 확인 창과 예상하지 못한 확인 창은 "취소"로 답하고 틀을 멈춘 뒤 창의 글을 큰 글씨로 보여 준다. 단순 안내 창(alert)은 내용을 활동 기록에 남기고 닫는다. 페이지 쪽 장치가 보내는 소식은 사이트가 흉내 낼 수 있으므로 **활동 기록과 "멈추기"에만** 쓰고, 제출 성공 판정이나 다음 단계 진행에는 쓰지 않는다(설계 6.8).

### 막힘·다시 기록 (TMPL-12)
- **D-28:** 요소를 못 찾거나(D-15) 화면이 예상과 다르면 그 자리에서 멈추고 `--warning` 카드로 이유를 보여 준다: [1 이 단계만 다시 기록] [Esc 멈춤](SYSTEM.md 상태 표). "이 단계만 다시 기록"을 고르면 이용자가 그 단계를 한 번 직접 하고, "이 단계를 이렇게 바꿀까요?" 확인(확인 화면 보호 적용) 뒤에만 틀에 반영한다. 반영하지 않으면 틀은 그대로다.

### 멈춰서 이용자가 직접 (TMPL-14~15)
- **D-29:** 민감한 칸이 들어 있는 틀은 실행 때마다 그 칸에서 멈추고 "이 칸은 직접 입력하세요"를 보여 준다. 이용자가 입력한 뒤 이어서 간다. 그 값은 틀·최근 값·활동 기록 어디에도 남지 않는다(TMPL-14, PRIV-01).
- **D-30:** 보안 키패드·자동입력 방지 문자(CAPTCHA)·결제 화면을 만나면 자동으로 누르지 않고 멈춘다. 이용자가 직접 한 뒤 이어서 가거나 멈출 수 있다. 판별 규칙은 단위 시험으로 고정하고, 연습 사이트에 흉내 낸 보안 키패드·자동입력 방지 문자·결제 화면을 둔다(설계 3장·8장). 보안 키패드를 대신 누르거나 자동입력 방지 문자를 풀지 않는다.

### 틀 파일 (TMPL-16)
- **D-31:** 틀을 파일로 내보내고 가져온다. 내보내기 전에 **"이 파일에는 틀에 저장된 고정 값이 들어 있습니다"**를 먼저 보여 주고 확인받는다. 파일에도 형식 버전을 붙이고, 가져온 파일은 zod로 검사한다. 검사나 형식 변환이 실패하면 지금 틀을 그대로 두고 알린다(설계 7장). 파일 저장·고르기는 Phase 3 설정 파일과 같은 방식(새 권한 없이)을 쓴다.

### 활동 기록 (LOG-01~03)
- **D-32:** 최근 2주 동안의 동작을 이 PC에만 남긴다: 무엇을 눌렀는지(요소 종류와 보이는 글자), 틀 진행(시작·단계·끝), 알림 창 내용, 막힘·확인 필요, 되돌리기. **입력한 값은 남기지 않는다** — 입력 단계는 "칸 '금액'에 입력"처럼 칸 이름만 남긴다. 알림 창 글과 보이는 글자에 들어 있는 주민·계좌·카드번호·전화번호 모양은 가려서 남긴다(설계 6.13, PRIV-01).
- **D-33:** 기록은 하루 단위 항목으로 나눠 `storage.local`에 저장하고(설계 7장), 14일이 지난 날은 지운다. 하루 항목이 무한히 커지지 않게 상한을 둔다.
- **D-34:** 명령판 셋째 장 3 "기록 내보내기"를 누르면 **내보낼 내용을 먼저 보여 주고**, 확인한 뒤 파일로 저장한다("저장했어요"). 기록이 없으면 "2주 동안 기록이 없어요", 저장 실패면 원인 + 다시 하기(SYSTEM.md 상태 표, LOG-02).
- **D-35:** 주간 진행 통계(LOG-03): 주마다 되돌리기 횟수, 틀 한 번에 이용자가 누른 횟수(틀 시작부터 끝까지 필터를 통과한 이용자 입력 수). 기본값을 조정하고 도우미가 실제로 나아지고 있는지 보는 데 쓴다(설계 6.13).

### 화면(오버레이)
- **D-36:** 모든 오버레이는 `docs/design/SYSTEM.md`(안 A 등대)와 `docs/design/tokens.css`만 따른다: Shadow DOM 안, 카드 radius 12·선택 시 남색 3px, 누르는 대상 높이 56px 이상, 번호 카드 = 큰 숫자(22px, 700) + 이름, 모든 버튼에 누를 키 칩, 막힘·확인 필요 = `--warning` 테두리 카드 + 이유 + 번호 선택지, 새 색·서체·radius·그림자 금지(디자인 검토, DESIGN.md §4).
- **D-37:** SYSTEM.md에 이미 있는 것: 확인 화면 템플릿, 명령판 카드 자리, 상태 표의 "틀 실행"·"기록 내보내기" 줄. **없는 것**(틀 저장 화면, 바뀌는 값 카드, 틀 목록, 진행 표시, 알림 창 글 보여 주기, 기록 미리 보기, 주간 통계)은 DESIGN.md §4-1대로 **먼저 SYSTEM.md에 템플릿을 더한 뒤** 만든다. 기존 토큰만 쓴다.
- **D-38:** 카피 규칙(SYSTEM.md): 질문 "…할까요?", 알림 "…했어요", 오류 "원인. 다음 행동.", 버튼은 사이트 버튼 이름 그대로("상신"), 키 이름은 영어(`Enter`, `Esc`)·스페이스바만 한글.

### 시험
- **D-39:** 모든 기능은 로컬 연습 사이트에서 먼저 시험하고, 실제 회사 시스템에서는 시험하지 않는다(설계 10장, 2026-09-23 사용자 결정). Phase 4용으로 연습 사이트에 더한다: 메뉴 → 양식 → 제출 → 결과 페이지로 이어지는 업무 흐름(날짜·금액·전화번호 칸), iframe 안 양식(같은 출처·다른 출처), 늦게 나타나는 입력칸, 모양이 바뀐 페이지(틀 막힘 재현), 결과가 불분명한 제출 버튼, 제출 뒤 확인 창 + 이어지는 두 번째 확인 창 + 안내 창, 민감칸, 흉내 낸 보안 키패드·자동입력 방지 문자·결제 화면.
- **D-40:** 단위 시험(설계 10장 명시분 + Phase 4): 요소 찾기 점수, 바뀌는 값 자동 표시, 제출 성격 버튼 판별, 보안 키패드·자동입력 방지 문자·결제 화면 판별, 실행 상태 이어 가기("누름"만 있으면 확인 필요), 알림 창 규칙(첫 확인 창만 확인), 활동 기록 가리기·14일 지우기·주간 통계, 틀 형식 검사·변환.
- **D-41:** 확장을 띄운 브라우저 시험(Chromium, `CI=true`): 틀 기록 → 저장 → 실행 → 제출 확인 → 막힘 → 다시 기록까지 흐름 전체, iframe 안 양식, 속도 바꾸기·Esc 멈춤, 알림 창 처리(틀 밖에서는 가로채지 않음 포함), 결과 불분명 → 확인 필요, **실행 중 service worker를 강제로 재운 뒤 이어 가기**, 같은 틀 두 번 실행 막기, 틀 내보내기·가져오기, 기록 내보내기 미리 보기, 주간 통계(설계 10장). 엣지·웨일은 수동 확인 목록.
- **D-42:** UI 완료 판정은 저장소 규칙대로: 싼 게이트(lint·typecheck·build) → 별도 에이전트의 독립 DOM 감사(`CI=true`, 스크린샷 육안 금지) → 수정 → 전체 게이트 한 번(CLAUDE.md). 이 단계는 외부 입력(가져온 틀 파일, 페이지 쪽 알림 창 소식)과 되돌릴 수 없는 제출을 다루므로 Post-build `/cso`는 필수다.

### Claude's Discretion
- 기록 단계의 정확한 모양(단계 종류, 같은 칸에 여러 번 입력하면 마지막 값만 남기기, 필요 없는 클릭 걸러내기)과 저장 형식.
- 바뀌는 값 모양(날짜·금액·전화번호)의 정확한 규칙과 오늘 날짜를 기록된 모양대로 만드는 방법 — 단위 시험으로 고정한다.
- 제출 성격 버튼 기본 단어 목록과 사이트별로 고치는 자리(위험 단어 목록과 같은 설정 구조를 쓸지).
- 요소 찾기 점수 기준값과 "충분한 차이"의 크기 — 단위 시험으로 고정한다.
- 속도별 쉼 길이(천천히의 멈춤 길이, 보통의 짧은 쉼)와 요소가 나타나기를 기다리는 최대 시간. Phase 2 결과가 있으면 따른다.
- 성공 메시지로 볼 글자(예: "완료", "저장되었습니다")와 결과를 기다리는 시간.
- "첫 확인 창"을 받아들이는 몇 초의 길이, 틀이 도는 중인지를 페이지 쪽 장치가 `document_start`에 바로 알 수 있게 하는 방법(연구가 정한다).
- 알림 창 `prompt`와 페이지 떠나기 확인(`beforeunload`)을 어떻게 다룰지 — 단, 틀 밖에서는 가로채지 않는다.
- 보안 키패드·자동입력 방지 문자·결제 화면 판별 신호(알려진 제품의 요소·주소·글자).
- 바뀌는 값의 최근 값을 몇 개·어디에 둘지(틀마다 따로 또는 Phase 3 최근 입력 값 재사용).
- 활동 기록 하루 상한, 항목 모양, 파일 형식(사람이 읽는 글 + 기계가 읽는 형식), 파일 이름.
- 주간 통계를 보여 줄 자리(예: 기록 내보내기 미리 보기 맨 위, 또는 옵션 페이지) — D-37 절차를 따른다.
- 틀 목록 관리(이름 바꾸기·지우기)를 어디서 할지(옵션 페이지 등) — 틀 지우기는 되돌릴 수 없으니 확인을 거친다.
- 메시지 타입 이름, 파일 배치, 형식 버전 올리는 방법.
