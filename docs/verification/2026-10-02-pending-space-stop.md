# 실행 대기 중 Space 정지

초기 기준: draft PR22 `9aa3b42dcd93ceb16de33282d12f7aff1b72753c`. CI79 보존 안내 회귀 수정 뒤 문서 충돌 정리까지 포함한 최종 기준은 PR22 `53162c9726167420dcf3a6005856cfc0a05f66e7`, 브랜치 `codex-switch-pending-stop`이다. PR21/22는 같은 안내 수정을 일반 push로 반영했으며 기존 검증 HEAD 이력은 보존한다.

## 문제와 동작

PR22 브라우저 검사에서 일반 요청 대기 중 Space가 쉬기로 처리되지 않는 경계를 실제로 확인했다. controller는 이제 `executing` 중 새롭고 신뢰할 수 있는 Space keydown을 기존 쉬기 처리로 전달한다. repeat·IME 조합·수정키는 정지로 해석하지 않는다. 정지 시 선택 시각을 갱신해 입력 간격 보호를 시작한다. 같은 keyup은 재개하지 않고, 보호 간격 이후 새 Space만 재개한다. 중단한 작업을 다시 보내지 않는다.

쉬기는 기존 모드 세대와 worker 취소 경계를 사용한다. 늦은 비교 응답은 확인 화면을 열지 않는다. 독립 검토에서 찾은 설정 응답 뒤 무조건 `up()`하는 경로도 세대를 확인해 늦은 응답으로 다시 진행하지 않게 했다. 이미 실행된 외부 효과를 되돌리는 기능은 아니므로 안내는 `쉬고 있어요. 이전 실행 결과를 확인하세요`이다. worker가 요청을 받기 전 모든 전송 지연에 대한 보장은 별도 범위다.

데이터 수집·저장 형식·권한·의존성·native/C# 범위는 늘리지 않는다. 기존 draft→명시적 apply 경계를 유지한다. merge/deploy·기존 설치 ZIP 교체는 하지 않는다.

## 재현 및 검토

- 첫 새 단위는 `executing`이 정지하지 않아 RED, 구현 뒤 GREEN.
- 검토 후 늦은 설정 응답과 즉시 입력 튐 두 테스트가 RED(기존13 pass), 각 세대 검사와 정지 시각 갱신 후15/15 GREEN.
- 경계는 같은 keyup, keydown/keyup 사이 늦은 응답, 자식 프레임의 반복·조합·수정키, 다음 새 입력의 재개만 포함한다.
- gpt-6.1-sol/high 독립 읽기 검토에서 설정 P2 수정과 입력 보호를 재확인했고 추가 P1/P2는 발견하지 못했다. 검토자는 테스트를 다시 실행하지 않았다.

## 단계별 실행 근거

- Space 정지 최종 구현의 type/lint/unit283/283 통과. 설정 응답·입력 보호 보완 전 1차 관련브라우저21/21(7.1분), 보완 후21/21(7.0분). 두 실행을 같은 소스 결과로 혼합하지 않는다.
- 보완 후 기본 UI101/101(4.1분, run-KWKkkc, fail/skip/flaky0).
- 이후 CI79가 안내 누락으로 실패해 PR21과 PR22에 안내 한 줄을 복원했다. 해당 PR21 소스의 기존복구6/6(1.6분) 통과. 이 후속의 Space 정지와 합친 소스에서 unit283/283 및 복구·이동취소·재적용11/11(3.0분)을 다시 통과했다. 이전 전체CI 실패를 성공으로 바꾸지 않는다.
- 안내 복원 후 최종 UI101/101(4.0분, run-FaNHaN, fail/skip/flaky0), type/lint/build exit0도 확인했다.
- 각 단계 소스 SHA256와 실행 수는 [구조화 결과](pending-space-stop-results.json)에 보존한다.

## 남은 범위

실제 Windows 한국어 IME, 실제 손 떨림/운동 사용성, 실제 사이트 검증은 미검증이다. 다음 클라우드 핵심 묶음은 Space 앞으로 이동/이동 불가 안내와 이동 요청 승인 경계 검토, 그 뒤 다중 스크롤 영역 선택 설계다. 사이트 임의 오류 원문·custom/radio/multiple 컨트롤·최근값/민감정보 자동수집·보호저장소를 무조건 확장하지 않는다. INPT-03 전체나 Phase3 완료로 표시하지 않는다.
