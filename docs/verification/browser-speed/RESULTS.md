**판단:** 버튼/스크롤/적용의 입력 이벤트 이후 처리 반응은 대부분 수 ms였으나, paused 작업판에서 원하는 명령을 선택하는 전체 경로는 수 초~수십 초였다. `가a1` 세 글자 작성도 약87초여서 자유로운 새 글 작성은 현재 빠르다고 보기 어렵다. 저장 문구와 빠른 설정은 줄여 주지만 메뉴 접근 비용이 남는다.

## 기본 설정에서의 작업 완료 시간

각3회, 순환1.5초·입력 보호0.3초. 모든 행은 준비된 페이지의 paused 작업판에서 시작한다. 중앙값 뒤 괄호는 최소–최대이며 총시간에는 순환 대기·확인 보호·자동화 검증이 포함된다. 표의 정지 행은 준비 경로를 포함한 시간이며 실제 정지 반응은 아래 별도 표를 본다.

번호 고정 최초 설정은 별도 **38.71초 (38.28–38.80), 7회**다. 고정 재사용은 reload 뒤 다시 paused에서 시작하며 reload는 재사용 시간에서 제외했다. 기본 단순 페이지의 첫 번째 버튼을 대상으로 했으므로 복잡한 목록에서의 탐색 이득은 측정하지 않았다.

번호 경로가 느린 이유는 `읽기·이동 → 고정 번호 → 1번 → 확인`의 메뉴 위치다. 첫 표본에서는 읽기·이동 선택 뒤 고정 번호가 활성화될 때까지 약18.5초가 걸렸다. 일반 경로 `페이지 항목 → 첫 버튼 → 확인`보다 메뉴 진입 자체가 길다. 제품의 `readingMenu()`에서 고정 번호는 뒤쪽 항목이고, 각 메뉴 첫 항목은 순환 주기의2배 머문다. 번호라는 이름만으로 더 빠르다고 결론낼 수 없다.

## 입력 이벤트 이후 반응

저장 문구 적용의171.4ms 표본을 그대로 포함했다. 해당 지연의 원인은 이번 bounded 측정으로 확정하지 않았다. 작업판 첫 DOM 변경은 경로별 중앙값0.8–2.0ms였다. 이는 각 Space 이벤트를 관측한 수치이며 동일 경로 안의 키들은 독립 표본이 아니다. 전체 유효 표본에서 최대47.4ms DOM 지연도 있었다. 스크롤 정지 뒤150ms 동안 위치 불변을 별도로 확인했다. 취소는 사이트 클릭0회를 확인했다.

탭 활성화·새 탭 내부 화면 표시의 최종 결과는 실제로 검증했지만, 이들의 입력→실행 완료를 동기화된 개별 이벤트 시간으로 분리한 수치는 없다. 해당 행은 전체 경로 시간과 작업판 DOM 반응만 제공한다.

## 개선 우선순위 — 구현하지 않은 제안

1. 자주 쓰는 작업으로 가는 메뉴 단계·순서를 먼저 줄인다. 고정 번호의18.5초 접근 대기와 탭 메뉴의 긴 대기가 근거다.
2. 새 글 작성의 선택 횟수와 그룹 접근을 줄이는 설계를 우선한다. 현 경로는3글자에도18회/86.6초다. 이미 있는 문구·양식 재사용의 활용 가능성을 함께 평가한다.
3. 순환 속도는 개별 이용자의 선택 성공률과 함께 조절한다. 0.8초 자동화에서는 약45% 단축했지만 실제 사용성은 별도다.
4. 이번 결과만으로 실행 엔진을 먼저 최적화할 근거는 약하다. 사이트 이벤트까지 대부분 수 ms였으며,171ms 지연 표본은 재현 조건을 더 확인해야 한다.

제품 소스 수정·merge·deploy·ZIP 교체 없이 측정만 했다. 7개 bounded 실행 모두 exit0, 실제 결과 조건 확인. 유효69표본(스위치39+직접 비교30), 제외12표본을 원본에 보존했다. 이전 전체 CI113을 재실행하지 않았다. 측정기 포함 최종 타입 검사·전체 린트 exit0을 확인했다. 실제 장애 사용자 속도·피로·Windows IME·실사이트 체감은 미검증이다.
