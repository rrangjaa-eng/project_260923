# 미완성 한글 조합 중 초안 편집 보호

## 이유와 범위

PR31/c0b277c의 일반 영문·숫자 입력은 CI100 unit401/browser407 success로 검증됐으며 draft·미병합이다. HEAD를 변경하지 않고 `codex-switch-compose-insertion`에서 후속을 분리한다. main9394b01은 유지한다. 사용자는 남은 안전한 구현·검토·push·draft PR·최종 CI의 계속 진행을 요청했으며 새 main 병합·배포는 승인하지 않았다.

PR31의 ASCII guard와 비교한 결과 기존 띄어쓰기·문구 삽입·앞/뒤 커서 이동·되돌리기가 initial/medial 조합을 유지한 채 draft.text/cursor/history를 바꿨다. 같은 문장 안에서 한글을 확정할 위치나 순서가 뒤틀리는 작은 기존 결함이다. 새로운 입력/저장 정책을 만들지 않고 PR31과 동일한 “조합을 마치거나 명시 취소한 뒤 다른 초안 편집” 보호를 적용한다.

## 동작 계약

- 미완성 한글이 있으면 `edit:space`, `edit:left`, `edit:right`, `edit:undo`, 숫자 인덱스의 문구 삽입만 ASCII와 같은 공통 진입부에서 거절한다.
- 안내는 “한글 조합을 마치거나 취소하세요”. 조합·초안·선택 위치·undo 이력·DOM을 보존하며 자동 확정이나 자동 취소하지 않는다.
- 조합을 마친 뒤 위 동작은 정상 실행된다. 명시 조합 취소 뒤에도 정상 실행된다.
- 조합 단계 삭제/취소, 명시 문장 버리기/새 문장, 읽기·쉬기·원래 적용 보호는 기존대로다. 문구 목록 조회·관리·저장 명령을 숫자 문구 삽입과 혼동하지 않는다.
- 새로운 권한·수집/영속 저장·외부 요청·native 연결은 없다. 회사 사이트·실제 PC 접근, 배포·ZIP 교체도 하지 않는다.

## 재현과 검증

순수 상태 엔진과 실제 controller/DOM을 사용하는 단위 검사에서 미완성 ㄱ+ㅏ 상태로 위5개 동작을 고르면 text/selection이 바뀌는 5RED를 확인했다. 예: 뒤 이동은 선택 위치2→3, 되돌리기는 가a나→가👍🏽나로 바뀌지만 조합은 그대로였다. 공통 guard를 적용한 뒤 관련18/18 GREEN. 각 검사는 차단 후 종성을 확정하고 정상 동작까지 확인한다.

타입·린트·전체 단위406/406(42파일) 통과. 새 Chromium2건과 PR31 기존4건, 기존 doc-editor/editor-frames, 자동UI·독립 검토·전체 CI의 최종 결과는 실행 종료 후 기록한다. 미실행/진행 중을 통과로 세지 않는다.

기존 panel과 안내 토큰만 사용한다. 스타일·레이아웃·인터페이스·메시지 schema·storage 경로는 바꾸지 않는다. 실제 Windows IME·운동 사용성·실사이트·native UI는 미검증이다. 전체 글쓰기 제품의 완료나 실제 기기 합격으로 확대하지 않는다.
