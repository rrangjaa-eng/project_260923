## Problem Statement

식당·공연·캠핑장 같은 예약 사이트는 빈자리가 언제 날지 모르고, 나면 금방 사라진다. 지금은 사람이 사이트를 계속 새로고침하다가 빈자리가 보이면 손으로 날짜·인원·예약자 정보를 넣고 신청한다.

이 도구는 **사이트와 조건(날짜, 시간대, 인원, 예약자 정보)을 양식으로 한 번 넣어 두면, 명령 한 줄로 실행해 빈자리가 날 때까지 확인하다가 조건에 맞는 자리가 나면 신청까지 끝낸다.**

첫 버전은 예약·신청만 다룬다. 반복 업무(회사 웹시스템 입력·조회)와 정보 수집은 같은 엔진 위에 나중에 붙인다.

## What Makes This Cool

기존 도구와 달라야 할 세 가지(브레인스토밍에서 사용자가 고름):
- **어떤 사이트든.** 사이트마다 만드는 예약 매크로와 달리, 조건만 넣으면 처음 쓸 때 Claude가 그 사이트용 실행 계획을 만들고, 그다음부터는 AI 없이 실행기가 그대로 돈다. 화면이 바뀌어 막히면 막힌 단계만 Claude에게 물어 고치고 저장한다.
- **신청까지 끝낸다.** 빈자리 알림 앱과 달리 알려 주는 데서 멈추지 않는다.
- **안전하게 자동.** Stagehand 같은 범용 도구와 달리 첫 실행 확인, 제출 재시도 금지 같은 예약 안전 규칙이 들어 있다.

덤으로, 쓸수록 AI를 덜 부르고 Claude 호출은 Max 요금제 안에서 하므로 평소 비용이 0원이다.

## Constraints

- **개인 도구.** 한 사람이 자기 컴퓨터에서 쓴다. 서버·웹 화면·여러 사용자는 없다.
- **실행은 명령 한 줄.** 정기 실행(스케줄러)과 웹 화면은 첫 버전 범위 밖이다.
- **입력은 양식.** 자유 문장이 아니라 정해진 항목으로 받는다(아래 "입력 양식").
- **Claude 호출은 headless Claude Code(`claude -p`)로, Max 요금제 안에서.** 모든 Claude 호출은 `ask-claude` 함수 하나를 거친다. 속도가 중요해지면 그 함수 하나만 Anthropic API 호출로 바꾼다. (비용 비교 스레드에서 사용자가 확정)
- **사이트 예의.** CAPTCHA·봇 차단은 우회하지 않는다. 만나면 멈추고 알린다. 빈자리 확인 간격은 사용자가 정하되 **30초 미만은 받지 않는다**(기본 1분).
- 저장소 규칙: 패키지 매니저 pnpm, TypeScript strict, `any` 금지, 시크릿은 코드·커밋 금지. 스택은 `/gsd-new-project`에서 확정한다.

## Premises

1. 첫 버전은 예약·신청 하나만 만든다. 세 가지 작업 종류가 같은 엔진(계획 → Playwright 실행 → 막히면 Claude 복구)을 쓰니, 한 종류로 먼저 검증한다. — 사용자 선택
2. 목표에 닿으면 신청까지 끝까지 자동으로 한다. 단, **새 작업의 첫 실행만 제출 직전에 멈춰 사용자가 확인**하고, 확인한 작업은 그다음부터 끝까지 자동이다. — 사용자 선택
3. 로그인은 사용자가 처음 한 번 `login <사이트>` 명령으로 연 브라우저 창에서 직접 한다. 도구는 그 로그인 상태(브라우저 프로필 폴더)만 재사용하고 비밀번호는 저장하지 않는다.
4. 카드번호 같은 결제 정보는 도구가 저장하지도 입력하지도 않는다. 사이트에 저장된 결제수단으로 끝나는 신청만 끝까지 자동이고, 새 결제 정보 입력이 필요한 화면을 만나면 멈추고 알린다.
5. Claude에게 보내는 페이지 정보에서 예약자 이름·연락처 등 작업 값은 자리표시자(`{{name}}` 등)로 바꿔 보낸다.

## Landscape (기존 도구 조사, 2026-09 웹 검색)

- **Stagehand** (Browserbase, TypeScript, MIT, v4.1): 행동을 디스크에 캐시해 다음 실행은 LLM 없이 재생하고, 캐시가 맞지 않으면 LLM을 다시 불러 스스로 고친 뒤 캐시를 갱신한다. 이 설계의 "한 번 계획, 재생, 깨진 단계만 복구"와 거의 같다. 클라우드 없이 로컬에서 돌고 LLM 클라이언트를 바꿔 끼울 수 있다. 단, v3부터 Playwright 대신 CDP로 Chrome을 직접 움직이고, 캐시·복구가 여러 단계짜리 계획 파일이 아니라 동작 하나 단위다. `claude -p`를 LLM 클라이언트로 끼울 수 있는지는 확인되지 않았다. (docs.stagehand.dev, npmjs.com/package/@browserbasehq/stagehand)
- **Playwright Test Agents** (1.56+, planner/generator/healer): 깨진 선택자를 고치는 healer가 있지만 테스트 파일용이다. 복구 프롬프트 방식만 참고할 수 있다. (playwright.dev/docs/test-agents)
- **browser-use / workflow-use**: 한 번 녹화, 결정적 재생, 실패하면 에이전트로 복구. Python이고 workflow-use는 아직 초기 단계다.
- **통념**: 예약 사이트는 화면(DOM)보다 사이트가 내부에서 부르는 JSON 요청으로 빈자리를 확인하는 편이 빠르고 덜 깨진다. 인기 예약 사이트는 봇 차단이 강하다.

## Cross-Model Perspective

독립 서브에이전트(같은 Claude, 이 대화를 보지 않음)의 의견 요약:
- 가장 멋진 버전: 계획을 만들 때 네트워크 요청을 기록해 빈자리를 돌려주는 JSON 요청을 찾아 두고, 반복 확인은 그 요청만 보낸다. 브라우저는 신청할 때만 띄운다. 확인이 약 10배 빨라지고 화면이 바뀌어도 덜 깨진다.
- 연습 실행 대신 "한 번 보여주기": 사용자가 `login` 창에서 직접 한 번 예약하면 그 과정을 기록해 계획으로 바꾼다.
- `task new`도 타이핑 대신 고르기: 날짜·시간대를 사이트에서 읽어 화살표로 고르게 한다. ("내가 질문에서 선택할 수 있게 하라고!")
- 엔진은 직접 만들지 말고 Stagehand에 `claude -p`를 끼워 실제 사이트 하나로 먼저 시험하라. 예약 전용 안전 규칙(첫 실행 확인, 제출 재시도 금지, 멈추는 경우 등)만 직접 만들면 된다.

종합: 캐시·자가 복구 엔진은 이미 있는 것을 쓰고, 이 도구만의 가치인 예약 안전 규칙에 힘을 쓰자는 데 동의한다. 다만 Stagehand가 `claude -p`와 붙는지, 동작 단위 캐시로 첫 실행 확인·확인 풀림 규칙을 지킬 수 있는지는 시험해 봐야 안다. JSON 요청 확인과 한 번 보여주기는 좋은 방향이지만 첫 버전에는 넣지 않고 다음 단계로 둔다.

## Approaches Considered

- **순수 스크립트** — 사이트마다 Playwright 스크립트를 손으로 짠다. AI 비용은 0원이지만 사이트가 늘 때마다, 화면이 바뀔 때마다 사람이 고쳐야 해서 "조건만 넣으면 된다"는 목표와 맞지 않아 제외.
- **완전 AI 에이전트** — 매 단계 Claude가 화면을 보고 판단한다. 가장 유연하지만 빈자리를 기다리며 반복 확인하는 이 용도에서는 확인할 때마다 비용과 시간이 들어 제외.
- **하이브리드를 Stagehand 위에** — 캐시·자가 복구를 Stagehand에 맡기고 예약 규칙만 직접 만든다. 만들 양이 가장 적지만 `claude -p` 연결과 확인 규칙 적용이 검증되지 않았다.
- **하이브리드를 Playwright로 직접** — 아래 계획 형식과 복구 규칙을 직접 만든다. 구조를 완전히 통제한다.

하이브리드 방식은 확정이다. **엔진을 Stagehand 위에 올릴지, Playwright로 직접 만들지는 `/gsd-new-project` 조사 단계에서 정한다**(사용자 결정).

아래에서 명령, 첫 실행 확인, 제출 규칙, 멈추는 경우, 입력 양식은 **어느 엔진이든 지켜야 할 동작**이다. "Claude가 페이지를 보는 방식", 실행 계획 형식, 복구 규칙의 세부(형식 검사·저장 시점·한도)는 **직접 만들 때의 설계**이고, Stagehand를 쓰면 그에 맞는 방식으로 같은 동작을 보장한다.

## Recommended Approach: 하이브리드

### 명령

| 명령 | 하는 일 |
|------|---------|
| `task new` | 입력 양식을 터미널에서 항목별로 묻고 작업 파일로 저장한다. |
| `login <사이트>` | 브라우저 창을 열어 사용자가 직접 로그인하게 하고, 로그인 상태를 그 사이트의 프로필 폴더에 남긴다. |
| `run <작업>` | 아래 흐름대로 실행한다. 같은 사이트는 한 번에 하나만 돈다(사이트별 잠금 파일). 두 번째 `run`은 이유를 알리고 끝난다. |
| `task resolve <작업>` | "확인 필요"로 끝난 작업의 실제 결과(신청됨 / 안 됨)를 사용자가 정리한다. 신청됨이면 "완료", 안 됨이면 다시 실행할 수 있게 된다. |

### 실행 흐름

```
run <작업>
  │
  ├─ 사이트 계획의 "탐색" 부분이 없으면 → ask-claude로 만든다
  ├─ "신청" 부분이 없으면 → 연습 실행: 조건과 상관없이 아무 빈자리로 신청 화면까지 가서
  │                        단계를 기록하고, 제출하지 않고 돌아온다 (빈자리가 하나도 없으면 건너뜀)
  ▼
  반복: 탐색 단계 실행 → 조건에 맞는 빈자리?
     ├─ 없음 → 간격만큼 기다렸다 다시 (마감 시각이 지나면 종료)
     └─ 있음 → 신청 단계 실행 (신청 부분이 없으면 이때 ask-claude로 만든다: 느린 경로)
                 ├─ 확인 안 된 작업 → 제출 직전 멈춤 (아래 "첫 실행 확인")
                 └─ 확인된 작업 → 제출 → 성공 판정 → 기록 후 종료
  어느 단계든 실패 → 단계 복구 (아래 "복구 규칙")
```

**Claude가 페이지를 보는 방식**: 실행기가 현재 페이지의 요약(접근성 트리 또는 정리된 DOM)과 목적을 `ask-claude`에 넘기고, Claude는 다음 단계들을 정해진 형식으로 돌려준다. 실행기가 그 단계를 수행하고, 목적에 닿을 때까지 이 주고받기를 반복한다. Claude에게 브라우저 도구를 직접 주지 않아 `ask-claude`를 API로 바꿔도 구조가 같다.

### 실행 계획 형식 (초안)

계획은 사이트 단위로 저장하고, 작업 값은 `{{변수}}`로 받는다. 같은 사이트의 다른 작업이 계획을 재사용한다.

**날짜 범위·여러 시간대**: 확인 한 바퀴마다 날짜 오름차순, 그 안에서 시간대 입력 순서대로 `search`를 한 번씩 돌리고, 처음 맞는 자리로 신청한다.

단계 종류: `goto`, `click`, `fill`, `select`, `waitFor`, `checkSlot`(조건에 맞는 빈자리가 있는지 판정하고 있으면 그 자리를 고른다. 남은 자리 수는 계획에 적힌 방법 하나로 읽는다: 요소 문구의 숫자, 속성 값, 또는 일치하는 요소 개수), `submit`(제출 버튼, 한 계획에 하나), `expectSuccess`(성공 화면 판정: URL 또는 문구).

```json
{
  "site": "example-camping.kr",
  "search": [
    { "type": "goto", "url": "https://example-camping.kr/reserve?date={{date}}" },
    { "type": "checkSlot", "selector": "td.available[data-time='{{timeSlot}}']", "min": "{{people}}", "count": { "from": "attr", "name": "data-left" } }
  ],
  "apply": [
    { "type": "fill", "selector": "#name", "value": "{{name}}" },
    { "type": "fill", "selector": "#phone", "value": "{{phone}}" },
    { "type": "select", "selector": "#people", "value": "{{people}}" },
    { "type": "submit", "selector": "button#confirm" },
    { "type": "expectSuccess", "text": "예약이 완료되었습니다" }
  ]
}
```

### 첫 실행 확인

- 확인 안 된 작업은 빈자리를 잡으면 `submit` 직전에 멈추고, 입력된 값과 화면 요약을 터미널에 보여 준 뒤 "제출할까요? (y/n)"를 묻는다.
- `y`면 **그 자리에서 바로 제출**하고 작업을 "확인됨"으로 바꾼다. 빈자리를 놓치지 않게 다시 실행할 필요가 없다.
- `n`이나 5분 동안 응답이 없으면 제출하지 않고 기록한 뒤 종료한다.
- 확인된 작업이라도 **Claude가 `checkSlot`이나 `apply` 단계를 고치면 확인이 풀린다.** 그 사이트의 모든 작업이 다음 제출 직전에 다시 멈춘다. 사람이 보지 않은 단계로 제출하지 않기 위해서다.

### 제출 규칙 (중복 신청 방지)

- `submit`을 누르기 직전에 "제출 시도"를 기록한다.
- `submit`은 절대 다시 시도하지 않는다. 결과가 불분명하면(시간 초과, 오류 화면, `expectSuccess` 불일치) "확인 필요"로 기록하고 종료한다.
- 이미 "제출 시도" 기록이 있는 작업은 `task resolve`로 결과를 정리하기 전까지 다시 실행하지 않는다.
- 신청에 성공한 작업은 "완료"로 표시하고 `run`이 다시 실행하지 않는다.

### 복구 규칙

- 단계가 실패하면 그 단계와 페이지 요약을 `ask-claude`에 넘겨 고친 단계를 받는다.
- 받은 결과는 계획 형식에 맞는지 검사하고, 맞지 않으면 실패로 센다.
- 고친 단계는 **실제로 실행해 성공한 뒤에만** 계획에 저장한다.
- 한도: 단계당 2번, 실행 한 번에 5번. 넘으면 멈추고 기록한다.
- 누르기 전에는 `submit` 선택자도 다른 `apply` 단계처럼 고칠 수 있다(확인이 풀린다). 누른 뒤에는 아무것도 다시 시도하지 않는다.

### 멈추는 경우

아래를 감지하면 아무것도 제출하지 않고 이유를 기록하고 종료한다.
- CAPTCHA·봇 차단 화면
- 새 결제 정보 입력 화면
- 로그인이 풀림(로그인 화면으로 이동됨) → `login <사이트>`를 다시 하라고 안내
- Claude 사용량 한도 등 `claude -p` 오류
- 브라우저 프로필이 다른 창에서 열려 있어 잠김 → 그 창을 닫으라고 안내
- 확인 간격보다 훨씬 늦게 깨어남(컴퓨터 절전 등) → 기록만 하고 계속 확인. 실행 중에는 컴퓨터가 깨어 있어야 한다.

### 입력 양식

타이핑보다 고르기를 우선한다. 첫 버전에서 고르는 항목은 날짜(달력), 인원, 확인 간격(1분·3분·5분·10분), 마감 시각(달력·시각)이고, 나머지는 입력한다. 시간대처럼 사이트마다 다른 선택지를 사이트에서 읽어 오는 것은 첫 버전 이후다. 항목: 사이트 주소, 날짜(또는 날짜 범위), 시간대, 인원, 예약자 이름, 연락처, 확인 간격, 마감 시각. 사이트마다 더 필요한 값은 "기타" 칸에 `이름=값`으로 자유롭게 넣고, 계획에서 `{{이름}}`으로 쓴다.

### 구성 요소

| 요소 | 하는 일 |
|------|---------|
| 작업 파일 | 양식 값, 상태(새 작업 / 확인됨 / 제출 시도 / 완료), 로컬 파일. |
| 사이트 계획 | 위 형식. 사이트 단위 로컬 파일. |
| `ask-claude` | 모든 Claude 호출의 유일한 입구. 지금은 `claude -p`, 나중에 API. 입력은 목적(탐색 계획 / 신청 계획 / 단계 고치기)과 페이지 요약, 출력은 계획 형식의 단계 목록. |
| 실행기 | 엔진(Playwright 직접 또는 Stagehand)으로 계획을 수행하고, 위 규칙대로 복구·확인·제출한다. |
| 결과 기록 | 실행마다 한 일, 멈춘 이유, Claude 호출 횟수. |

## Open Questions

1. **첫 대상 사이트는 어디인가?** 실제 사이트 하나가 정해져야 첫 계획과 성공 기준을 검증할 수 있다. 가장 먼저 필요한 답이다.
2. 신청했을 때 사용자에게 어떻게 알릴까? 첫 버전은 터미널 출력과 결과 기록만 두고, 휴대폰 알림은 나중으로 둔다(기본값).
3. 첫 대상 사이트의 봇 차단은 얼마나 강한가? 이 도구는 차단을 우회하지 않으므로, 차단이 강한 사이트는 대상에서 빠질 수 있다.
4. 신청 화면에서 단계가 깨졌을 때 `claude -p` 호출이 빈자리 경쟁에 충분히 빠른가? 연습 실행으로 대부분 미리 막지만, 실제로 느리면 `ask-claude`를 API로 바꾼다.

## Success Criteria

1. 실제 예약 사이트 하나에서, `task new`로 작업을 만들고 `run` 한 번으로 빈자리를 찾아 제출 직전에 멈추고, `y`를 누르면 그 자리에서 신청이 끝난다.
2. 같은 사이트로 두 번째 실행부터는 Claude 호출이 0번이다(결과 기록으로 확인).
3. 저장된(캐시된) 탐색 단계 하나를 일부러 망가뜨리면, Claude를 불러 고치고 이어서 실행하며, 고친 선택자가 저장되어 다음 실행에서는 다시 부르지 않는다.
4. 빈자리 판정 단계나 신청 단계 하나를 일부러 망가뜨리면, 고친 뒤 제출 직전에 다시 멈춘다(확인이 풀림).
5. CAPTCHA, 새 결제 정보 입력, 로그인 풀림을 만나면 아무것도 제출하지 않고 멈추며 이유를 기록한다.
6. 제출 결과가 불분명하면 다시 제출하지 않고 "확인 필요"로 끝난다.

## What I noticed about how you think

- 질문을 글로 받자 바로 "내가 질문에서 선택할 수 있게 하라고"라고 했다. 이 도구가 없애려는 것도 같은 종류의 수고, 즉 사람이 매번 손으로 채워 넣는 일이다.
